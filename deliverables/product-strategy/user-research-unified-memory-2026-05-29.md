# MemHop 统一记忆架构 — 用户研究综合报告

**日期**：2026-05-29
**类型**：用户研究综合
**作者**：瑞思（Reese）· 用户研究员
**输入**：统一记忆架构愿景文档（15 个场景）

---

## 📌 研究方法说明

本报告基于愿景文档中列出的 15 个场景进行推断性用户研究（inferred UX research）。由于当前阶段缺乏直接的终端用户访谈数据，分析采用以下方法论：

- **场景反向推导**：从架构能力反推用户行为模式和真实痛点
- **显性/隐性需求分离**：区分"用户说的"（surface-level ask）和"用户做的/感受到的"（underlying need）
- **JTBD 框架**：每个场景落在"用户雇佣 MemHop 完成什么任务"的框架内
- **跨场景模式识别**：识别 15 个场景之间的共性和差异

## 1. 通用个人用户（场景 1-8）

### 1.1 用户画像速写

通用个人用户是 MemHop 当前的主要用户群，典型画像为：

- **技术人**：开发者、工程师、技术写作者。日常工作涉及大量代码、技术文档、踩坑记录
- **知识工作者**：需要持续阅读（书/论文/文章）并产出的人
- **有"第二大脑"需求的人**：已经意识到个人知识管理的重要性，但被工具碎片化困扰

### 1.2 核心场景矩阵

| 场景 | JTBD（任务） | 输入行为 | 期望输出 | 当前状态 |
|------|-------------|---------|---------|---------|
| 1. 读技术书 | "我想记住这本书的内容，以后能自然召回" | mount PDF → 偶尔 recall | 书中的段落和相关讨论一起出现 | ⚠️ 裂脑 |
| 2. 读论文 | "论文的核心结论、方法、数据，我需要的时候能找到" | mount/拖入 PDF | 论文片段 + 自己的笔记一起召回 | ⚠️ 裂脑 |
| 3. 写项目 | "我上次遇到的那个 bug 怎么解决的来着" | 对话中自动 store | 精确召回当时的上下文 | ✅ |
| 4. 挂项目文档 | "项目的配置、流程、踩坑记录，一个 query 全出来" | mount /docs | 文档 + 对话经验混合结果 | ⚠️ 裂脑 |
| 5. 日常聊天 | "我上周是不是说要学 Rust" | 对话自动 store | 模糊的意图记忆被召回 | ✅ |
| 6. 浏览网页 | "那篇关于 tokio 调度器的文章说了什么" | 浏览器插件 → store | 文章要点 + 当时为什么觉得重要 | ✅ |
| 7. 看视频/播客 | "那期播客里提到的那个观点" | 转录 → store | 播客观点，即便原始措辞已模糊 | ✅ |
| 8. 多项目交叉 | "项目 A 的方案能不能用在项目 B" | 自动 store + 手动 link | 跨项目的模式识别和迁移建议 | ✅ + 增强 |

### 1.3 显性 vs 隐性需求

#### 用户说的（显性需求）

> "为什么我挂载了这本书，recall 的时候搜不到里面的内容？"
> "Shelf 重启就丢了，每次都要重新挂载，烦死了。"
> "我得先 recall 聊天记录，再 separately knowledge_search 书的内容，然后自己拼接。"

这些都是**功能层面的抱怨**——用户直接指出了当前裂脑架构的不便。

#### 用户做的（行为模式揭示的隐性需求）

但更深层的需求藏在行为里：

1. **用户挂载书/论文后，接下来几乎总是会在对话中讨论它**。这说明他们不是在做"文件索引"（那是 Spotlight/Alfred 的事），而是在做"理解消化 + 建立关联"。
   - **隐性需求**：不是"全文搜索"，而是"我读过的内容 + 我的理解 + 我的讨论"三者融合。

2. **用户会在多个项目之间来回切换**（场景 8 多项目交叉）。他们在项目 A 学到的东西，希望在项目 B 自动浮现。
   - **隐性需求**：不是"按项目分桶"（那是文件夹思维），而是"跨项目模式识别"——大脑的类比推理机制。

3. **用户经常在挂载文档后的数天甚至数周才 recall**（"我明明挂载过那本书"）。这说明外部知识的使用节奏与对话不同——文档是"知识储备"，对话是"即时交互"。
   - **隐性需求**：不是"实时索引"，而是"持久记忆"——挂载一次，永久可用，随时间巩固而非衰减。

4. **用户挂载的是"希望以后用到的"，而不是"现在立刻要查的"**。这和搜索引擎的行为模式完全不同。
   - **隐性需求**：不是"按需搜索"，而是"预加载到记忆"——把外部知识变成自己记忆的一部分。

### 1.4 关键痛点排序

| 排名 | 痛点 | 频率 | 影响 | 根因 |
|------|------|------|------|------|
| 🔴 P0 | Shelf 与主记忆分离，recall 不返回文档内容 | 每次挂载文档后 recall | **高** — 用户需要手动两次 MCP 调用并自行拼接 | 裂脑架构 |
| 🔴 P0 | Shelf 重启丢失 | 每次重启 | **高** — 用户对系统可靠性丧失信心 | 内存 HashMap |
| 🟠 P1 | 无法关联"读过的内容"与"聊过的天" | 讨论文档相关内容时 | **中高** — 错失最重要的洞察（记忆涌现的核心价值） | EntangleGraph 不跨类型 |
| 🟠 P1 | 跨项目模式识别缺失 | 多项目并行时 | **中** — 用户需要自己意识到"这和之前那个项目类似" | EntangleGraph 未被充分利用 |
| 🟡 P2 | Dream 不处理外部知识 | 长期 | **中** — 挂载的知识不会自动巩固、关联、摘要 | Shelf 独立存储 |
| 🟡 P2 | 两份索引内存占用 | 一直 | **低** — 用户感知不到，但限制了可挂载文档数量 | 两份 HNSW |

### 1.5 期望体验

> **"我想挂载一本书，聊几句，一周后问任何一个相关问题，系统不仅能找出书里的原文，还能告诉我当时我读了这部分后有什么想法，以及这和我另一个项目的经验有什么关联。"**

翻译为产品语言：
- **一次 recall，混合返回**：不区分来源（对话/文档/网页），按语义相关度统一排序
- **自动关联**：系统主动发现"这段书的内容"和"上次聊的踩坑经验"有关联
- **持久可靠**：挂载一次，永远在（跨重启、跨设备）
- **渐进增强**：越是反复 recall 某段知识，它越容易被找到（Hebbian 学习）

### 1.6 优先级建议

通用个人用户是 **v0.10.0 统一存储重构的首要受益者**。他们所有的痛点（P0-P2）都在 Phase 1 的范围内解决。建议：

1. **P0 必须 v0.10.0 解决**：统一 recall + LMDB 持久化
2. **P1 需要 v0.10.0 实现**：EntangleGraph 跨类型关联（这是差异化价值的核心）
3. **P2 可以在 v0.10.0 中顺带解决**：Dream 支持 Knowledge engram

## 2. 专业领域用户（场景 9-13）

### 2.1 用户画像速写

| 领域 | 典型用户 | 核心工作流 | 记忆需求特征 |
|------|---------|-----------|------------|
| 法律 | 律师、法务、法官助理 | 案例检索 → 判例比对 → 裁判要旨提取 | 精确、可溯源、时效敏感 |
| 医学 | 临床医生、医学研究员 | 指南查阅 → 病例匹配 → 诊疗路径 | 证据等级、时效性、权威性 |
| 学术 | 研究生、教授、研究员 | 文献综述 → 研究方向追踪 → 引用链 | 文献关联、研究方向聚类 |
| 金融 | 分析师、投资经理 | 研报分析 → 行业判断 → 标的跟踪 | 时效敏感、标的关联、多源交叉验证 |
| 企业 | 运维、项目经理、HR | SOP 查阅 → 流程执行 → 决策历史 | 版本控制、权限控制、团队共享 |

### 2.2 领域独特需求（场景 × 领域分析）

#### 场景 9：法律 — 案例库

- **用户说的**：「我需要查找与当前案件类似的判例，看裁判要旨」
- **用户做的**：在裁判文书网上按案由/法条搜索 → 逐个打开 PDF → 人工比对
  - **隐性需求**：不是"关键词搜索"，而是"法律逻辑相似的判例"——同一个法条在不同情境下的适用方式
- **MemHop 独特价值**：
  - 自定义 chunker：按"条款 + 判例号"而非按段落切分
  - 自定义 meta：案件编号、法院层级、裁判日期、适用法条
  - 自定义 ranker：同法院 > 上级法院 > 同级其他法院；近期 > 远期
- **差异化**：通用搜索引擎做不了"同法院近期类似判例"的加权排序

#### 场景 10：医学 — 临床指南

- **用户说的**：「某疾病的诊疗路径是什么，最新指南怎么说」
- **用户做的**：查 UpToDate/指南 PDF → 按病症查找 → 看证据等级 → 结合病人情况判断
  - **隐性需求**：不是"全文搜索"，而是"证据等级加权的精准答案"——A 级证据优先于 C 级
- **MemHop 独特价值**：
  - 自定义 chunker：按病症 + 指南章节切分
  - 自定义 meta：疾病分类、指南等级 (A/B/C)、发表年份
  - 自定义 ranker：证据等级 0.5 + 时效性 0.3（旧的指南可能已过时）
- **关键洞察**：医学用户对"权威性"和"时效性"的双重要求是独特的——不会因为一段文字语义匹配度高就采纳，必须看来源等级

#### 场景 11：学术 — 文献综述

- **用户说的**：「帮我梳理这个研究方向的最新进展」
- **用户做的**：在 Google Scholar/ArXiv 搜索 → 下载几十篇 PDF → 逐篇标注 → 手写综述
  - **隐性需求**：不是"论文检索"（Scholar 已经做得很好），而是"发现论文之间的关联"——谁引用了谁、谁反驳了谁、不同方法之间的演进关系
- **MemHop 独特价值**：
  - EntangleGraph 自动发现论文间的引用/主题关联
  - 跨论文语义链接（"这篇的结论和那篇的实验结果一致"）
  - 自定义 meta：作者、年份、会议/期刊、被引次数
- **关键洞察**：学术用户最痛的点不是"找不到论文"，而是"读了 50 篇，记不住每篇的核心观点和它们之间的关系"。这是纯记忆系统的强项。

#### 场景 12：金融 — 研报分析

- **用户说的**：「帮我找到关于新能源行业的最新判断」
- **用户做的**：在多平台下载研报 → 按行业/标的分类 → 对比不同券商观点 → 形成自己的判断
  - **隐性需求**：不是"研报搜索"，而是"多源交叉验证"——同一标的不同券商的评级差异、同一行业不同时间点的判断变化
- **MemHop 独特价值**：
  - 自定义 chunker：按公司/板块切分
  - 自定义 meta：股票代码、行业分类、报告日期、券商
  - 自定义 ranker：时效性偏重（研报时效性极强）
- **关键洞察**：金融研报的"半衰期"极短——三个月前的判断可能已完全失效。需要 vitality 衰减策略配合。

#### 场景 13：企业 — 内部 SOP

- **用户说的**：「某流程的标准操作是什么」
- **用户做的**：打开 Confluence/飞书文档 → 搜索 → 找到可能已过时的文档 → 问同事确认
  - **隐性需求**：不是"文档搜索"，而是"当前有效的操作流程 + 历史决策背景"——知道"为什么这么做"比知道"做什么"更重要
- **MemHop 独特价值**：
  - 自定义 meta：部门、流程类型、版本、审批人
  - 决策历史 + SOP 混合召回（聊天中讨论过的流程变更 + 文档中的正式版本）
- **关键洞察**：企业场景是"通用个人"和"协作用户"的交集——既需要个人记忆，又需要团队共享。

### 2.3 共通需求 vs 领域特有

#### 所有垂类的共通需求

| 需求 | 说明 | 架构对应 |
|------|------|---------|
| 自定义切分策略 | 不同领域的文档结构不同，不能一刀切段落 | `chunk()` trait |
| 结构化元数据 | 领域特有的分类字段（法条、疾病、股票代码…） | `extract_meta()` trait |
| 领域加权排序 | 通用语义匹配不够，需要按领域规则重排 | `ranking_bias()` trait |
| 可溯源 | 专业用户需要知道"这个信息来自哪个文档、哪个版本" | meta 中的 source 字段 |
| 批量导入 | 几百个 PDF 不可能逐个挂载 | 批量 mount 目录 |

#### 领域特有需求

| 领域 | 特有需求 | 为什么通用方案不够 |
|------|---------|-------------------|
| 法律 | 法院层级加权、法条关联 | 通用相似度不区分"最高法判例"和"基层法院判例" |
| 医学 | 证据等级分层、禁忌联动 | 错误的诊疗建议可能致命，需要权威性门控 |
| 学术 | 引用链追踪、研究方向聚类 | 论文的价值不仅在其内容，还在其引用关系 |
| 金融 | 时效性极度敏感、标的关联 | 三个月前的研报可能已是噪音 |
| 企业 | 版本控制、权限分层、审批流 | 不是所有人可以看到所有文档 |

### 2.4 优先级建议

专业领域用户是 **Phase 2（v0.11.0）的重点**。但需要注意：

1. **Phase 1 已经为垂类铺路**：统一存储后，自定义 chunker/meta/ranker 只需要实现 trait，不需要动核心里程
2. **建议 v0.11.0 内置 Law 和 Medical 两个示例**：前者验证结构化元数据的价值，后者验证权威性门控的必要性
3. **学术和金融可以作为 Custom 示例文档发布**：不需要改代码，只需要配置 JSON
4. **企业场景应推迟到 Phase 3**：企业需要多用户权限，这不是 v0.11.0 的范围

## 3. 协作场景（场景 14-15）

### 3.1 用户画像速写

| 场景 | 典型用户 | 典型上下文 |
|------|---------|-----------|
| 团队共享知识 | 小团队（3-10人）的技术负责人、项目经理 | "团队的知识不能只在我一个人的脑子里" |
| 多设备同步 | 跨设备工作的个人用户 | "我在手机上读的书，电脑上应该自动有" |

### 3.2 显性 vs 隐性需求

#### 场景 14：团队共享知识

**用户说的**：
> 「我希望团队其他人也能用我挂载的文档」
> 「团队的决策历史应该所有人可见」

**用户做的**：
- 在 Slack/飞书上把重要决策贴到公告频道（手动扩散）
- 写会议纪要，但很少有人回头看
- 新人入职时靠老员工口述历史

**隐性需求**：
1. **机构记忆（Institutional Memory）**：团队的决策、踩过的坑、积累的知识不随人员流动而丢失。这是比"共享文件"更深层的需求。
2. **上下文传递**：新人加入时，不需要逐个问老人——系统自动提供"这个项目之前的关键决策和讨论"。
3. **权限分层**：不是所有记忆都适合全员可见——有些踩坑记录可能涉及敏感的客户信息或技术债讨论。

**关键洞察**：团队真正需要的不是一个"共享文件夹"，而是一个"共享海马体"——每个人的对话记忆、阅读记忆、决策记忆，经过权限过滤后，可以被团队的其他人 recall 到。

#### 场景 15：多设备同步

**用户说的**：
> 「我在手机上看的书，电脑上应该能搜到」
> 「多台电脑之间的记忆应该同步」

**用户做的**：
- 用 iCloud/Dropbox 同步文件
- 用 Git 管理笔记仓库
- 在不同设备上重复挂载同一份文档

**隐性需求**：
1. **无缝连续性**：用户不把"设备"当成边界——记忆应该跟着人走，不跟着设备走
2. **离线优先**：用户在飞机上读的书、在地铁里做的笔记，在离线状态下也应该可用
3. **冲突处理**：两台设备上对同一份记忆的操作不应该互相覆盖

**关键洞察**：用户真正的需求不是"文件同步"（已有无数工具做这个），而是"记忆同步"——你的对话、阅读、思考的痕迹在不同设备间无缝延续。

### 3.3 协作场景的复杂性

| 维度 | 简单方案 | 实际需求 | 差距 |
|------|---------|---------|------|
| 共享粒度 | 整个 DB 共享 | per-shelf / per-meta 权限 | 大 |
| 冲突处理 | 最后写入胜出 | 特定场景需要合并 (CRDT) | 大 |
| 离线支持 | 在线 only | 离线可读，上线后同步 | 中 |
| 身份认证 | 无（单用户） | 多用户身份 + 权限体系 | 大（新增能力） |
| 数据安全 | 本地文件（物理安全） | 共享后需要访问控制 | 大 |

### 3.4 优先级建议

协作场景是 **Phase 3（v1.0.0）的内容**，但 Phase 1-2 的架构决策需要预留空间：

1. **Phase 1 需要做的预留**：
   - meta 中预留 `owner` 和 `visibility` 字段（先 hardcode 为 `owner: "local_user"`, `visibility: "private"`）
   - 不做权限逻辑，但不在数据结构层面堵死

2. **Phase 3 需要解决的问题**：
   - 最简单的多设备同步：文件级 LMDB 复制（让用户自己用 iCloud/Git），单写多读
   - 最简单的团队共享：共享 schema + 只读 access token
   - **不做**：实时协作编辑、CRDT、完整的 RBAC

3. **风险提示**：协作场景如果做重了，可能会拖累整个产品的简洁性。MemHop 的核心价值是"个人的记忆涌现"，团队共享应该是一个"轻量附加功能"，而不是主赛道。

## 4. 跨场景模式识别

### 4.1 所有用户都想要的（共通核心）

通过分析 15 个场景，以下需求跨越所有用户类型：

| 共通需求 | 跨场景证据 | 产品含义 |
|---------|-----------|---------|
| **统一入口** | 场景 1-15 都要求一次 recall 返回所有相关记忆 | recall API 不能区分来源 |
| **持久可靠** | 场景 1,2,4,9-13 都涉及"挂载一次，长期可用" | LMDB 持久化是底线，不是特性 |
| **自动关联** | 场景 1,2,8,11,14 都涉及"发现意想不到的关联" | EntangleGraph 是核心差异化价值 |
| **可信来源** | 场景 9-13 都要求知道信息出处 | meta.source 和 shelf context 是刚需 |
| **渐进增强** | 场景 1,3,8 越常用的记忆越容易被找到 | Hebbian 学习 + Dream 巩固 |

### 4.2 用户分层金字塔

```
           ┌──────────────┐
           │ 协作团队       │  ← Phase 3 (v1.0.0)
           │ 10-100 用户    │    多用户 + 权限 + 同步
           ├──────────────┤
           │ 专业领域       │  ← Phase 2 (v0.11.0)
           │ 法律/医学/学术  │    ShelfDomain trait + 示例
           ├──────────────┤
           │ 深度个人用户    │  ← Phase 1 (v0.10.0)
           │ 读书 + 聊天     │    统一 recall + EntangleGraph 跨类型
           ├──────────────┤
           │ 基础个人用户    │  ← 当前状态
           │ 纯对话记忆     │    store/recall 可用
           └──────────────┘
```

每一层用户的需求是上一层的子集。这意味着：
- Phase 1 解决了 **最大基数用户** 的核心痛点
- Phase 2 为 **高价值垂类用户** 打开大门
- Phase 3 解锁 **网络效应**

### 4.3 用户行为中的反直觉发现

1. **"挂载"行为的本质不是"搜索"而是"预记忆"**
   - 用户挂载文档时，不是要立刻搜索它——而是希望"以后用的时候能自然想起来"
   - 这意味着 chunk 质量 > 索引速度，记忆持久性 > 实时性

2. **用户不想要"更强大的搜索"，想要"更自然的记忆"**
   - 对比：Spotlight/Everything 是搜索工具，你主动去搜
   - MemHop 是记忆系统，你在对话中自然想起
   - 产品定位应强调"记忆涌现"而非"语义搜索"

3. **专业用户对"通用 AI"的怀疑在加深**
   - 法律和医学用户不会信任通用 LLM 的回答，但会信任"从我挂载的权威文档中检索到的内容"
   - 这意味着 MemHop 的垂类价值不在"AI 能力"，而在"检索精度 + 来源透明"

## 5. 风险与机遇

### 5.1 用户侧风险

| 风险 | 严重性 | 缓解措施 |
|------|--------|---------|
| 个人用户被"统一"的复杂性吓退 | 中 | 核心 API 不变，统一是内部实现，用户感知的是"recall 返回更多有用结果" |
| 垂类用户觉得自定义门槛高 | 中 | 提供内置示例（Law/Medical）+ 文档 + JSON 配置模式 |
| 协作用户期待完整的协作功能但只得到文件级同步 | 低 | 在 Phase 3 中明确 Non-goals，管理期待 |
| Knowledge engram 数量膨胀导致 recall 质量下降 | 中 | 需要验证 100K+ engram 时的 HNSW 精度（愿景文档已提及） |

### 5.2 用户侧机遇

| 机遇 | 价值 | 切入点 |
|------|------|--------|
| "记忆涌现"的 wow moment | 高 — 用户首次看到系统自动关联了以为不相关的两件事 | Phase 1 EntangleGraph 跨类型 |
| 垂类用户的"信任锚点" | 高 — 专业用户看到来源标注、权威等级，建立对产品的信任 | Phase 2 Law/Medical 示例 |
| 个人 → 团队的传播路径 | 高 — 个人用户用得好，自然会推荐给团队 | Phase 3 轻量共享 |
| "第二大脑"叙事的差异化 | 中 — 市面上第二大脑工具很多，但都没有真正的"记忆涌现" | 产品叙事中强化 Hebbian/Dream |

## 6. 行动建议（给产品团队）

### 6.1 立即行动（v0.10.0）

1. **统一 recall 是最高优先级**：这是所有用户层共同的最大痛点
2. **EntangleGraph 跨类型关联必须在 v0.10.0 中实现**：这是差异化价值的核心，不是"下一阶段再做"的事
3. **LMDB 持久化 Shelf 内容**：用户对"重启丢失"的抱怨是最直接的

### 6.2 数据驱动的下一步

在进行 v0.11.0 垂类扩展之前，建议收集以下用户数据：

1. **当前 Shelf 使用数据**（如果可采集）：挂载最多的文档类型？平均挂载数量？recall 频率？
2. **对话中的"后悔"信号**：Agent 在对话中说"我没有相关信息"时，用户是否表现出 frustration
3. **潜在垂类用户访谈**：找 3-5 个法律/医学/学术用户，做概念验证演示，收集反馈

### 6.3 产品叙事建议

面向用户的统一记忆叙事应该是：

> **"挂载一本书，它就成为你记忆的一部分。不是搜索，是记忆。"**

而非：

> "我们重构了存储架构，把 Shelf 融入了主引擎"（这是技术叙事，用户听不懂也不需要懂）

## 7. 后续研究建议

本报告是基于架构愿景文档的推断性分析。以下问题需要在真实用户研究中验证：

1. **个人用户是否真的有"跨项目模式识别"的需求**——还是他们更希望项目之间保持隔离？
2. **法律/医学用户对 AI 辅助检索的信任阈值**——什么条件下他们会信任系统的召回结果？
3. **团队共享的最小可行方案**——用户能不能接受"只读 token + 手动同步"，还是需要完整的实时协作？
4. **Knowledge engram 的 vitality 衰减**——外部知识和对话记忆是否应该用不同的衰减曲线？
5. **mobile 场景的特殊需求**——手机上的记忆行为（短文本、碎片化、语音输入）和桌面端有何不同？
