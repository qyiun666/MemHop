# 决策档案: 一轮的计划和这一轮的内容各走各的写面

Status: implemented

Superseded by: 2026-09-10-plan-step-addressed-by-ordinal.md

## Problem

宿主跑的是一个 LLM loop：每一轮先读场景拿到本轮的话题 id，让模型规划「当前执行哪些步骤」，
把每一步做过的事记成事件并绑到某一步上，那一步做完就分析结果、进下一步，最后收口本轮话题。
计划因此**每轮重述一次**——同一个步骤编号在第 2 轮和第 4 轮指的是同一件事，但第 4 轮可能已经
把它拆成了三层子步。

档案 `2026-09-09-turn-topic-id-is-the-only-join-key.md` 早就把「跨轮持续演化的计划树」列为放弃项，
并把替代手段写成「宿主自己每轮回放计划」。这条替代手段当时没有工具支撑：唯一的计划写面一次只
推进一个节点，而且**强制绑一条事件**（事件侧正文与事件名都非空才过闸）。于是要把计划重述成
`1,2,3.1,3.2,3.3,4`，宿主得发六次调用，其中给早已完成的 `1`、`2` 各得**编造一条不存在的事件**
才能把完成状态落进这一轮。写面的形状让"回放"这个官方推荐动作付出 O(步骤数) 次调用加同样多条
假事件。

同一时刻还有一件反着的事：追加事件时如果 `NodePath` 指向一个不存在的步骤，库会顺手把那一步
连祖先一起建出来。这在「计划是宿主意图的记录」这个定位下是错的：它让一条记录能凭空创造计划，
而产品语义要的恰恰相反——步骤按计划执行，所以计划必须先于步骤存在。这一条还是当时的已知代价，
档案里写着「打错一段路径会凭空多出一棵树，而计划层没有删节点的入口」。

## Decision

- **计划由声明产生，不由提交拼出**：一次调用交入本轮规划的整批步骤（点号路径任意深度，路径上
  缺失的段按 pending 建出来），一步的状态与文案就在这一条里说完。存储形状不变——仍然一节点一条
  记录、仍按 (轮次话题, 路径) 派生身份。
- **声明只说它列出的东西**：没被列出的节点保持现值。撤回一步的手段是下一轮声明一棵新树。
- **节点只由声明建立**：事件绑到一个树上没有的步骤，整条记录在任何落盘之前被拒。
- **一步的轨迹按子树取**：`NodePath` 读侧条件命中该步本身以及它下面的每一层。
- **节点不描述自己是什么类型**：`Title`/`Summary` 说这一步是什么，工具名住在该步事件的 `EventType`
  里；`Status` 只有四个值，`in_progress` 是「正在做」的唯一说法，且**不设状态迁移表**——声明式写面
  下状态是宿主给出的事实，库不裁决它能不能跳。
- **父节点的摘要等全部直接子到达终态才折**，且只回填空摘要；被重述回非终态的步骤失去它的完成时间。
  摘要文本由宿主在声明里带，**计划层不调用 LLM**。
- **一轮一棵树、一个话题一棵树这条键规则不动**：轮次话题 id 仍然是 L2/L4/L5 唯一的 join key。

## Alternatives considered

- **计划树改挂场景 id（一个会话一棵树，跨轮原地演进）**——落选：与 `turn-topic-id-is-the-only-join-key`
  冲突，且会让「一步的轨迹」跨键——事件按轮存、节点按场景存，"这一步做过什么"再也不能由一个键
  取回。宿主选的是每轮重述，而重述在键上天然干净。
- **恢复整棵快照的 diff 同步（快照里没出现的节点即删除）**——落选：`6c1aa7d` 的理由没有被任何新
  事实推翻——部分重述与完整重述在库这边长得一模一样，猜错就是静默删掉宿主的一步；而且它今天仍然
  需要回答「未列出的算什么」，而换轮次键已经免费回答了这个问题的全部实际用途。
- **保留逐步提交、只把事件改成可选**——落选：解开假事件那一半，剩下"每轮 N 次调用"和"节点能被
  两条路径创建"两个问题原样留着；同一功能两个实现也是它自己的死因。
- **父节点完成时由库调 LLM 压缩该子树的事件产摘要**——落选：节点完成与本轮话题的蒸馏是两件不同的
  事，后者已有归属（`Update`）；在锁内的计划写面上加一次 LLM 往返，换来的是宿主本来就知道的一句话。
- **给 `L4Query` 再加一个「精确匹配本步」开关**——落选：动作几乎都落在叶子步骤上，"这一步做过什么"
  的自然单位就是子树；为拿不到「只属于父节点自己那一行」那个切面多留一个布尔，是两个条件描述一件事。
- **给树加节点级删除接口**——落选：声明语义下它没有独立的用途（未列出即不在本轮计划里），而一个
  只服务于「同一轮内改主意」的删除口会把「不猜消失」这条判据重新搅浑。

## Consequences

- 换来：一轮的热路径调用数从「每步一次」降到「每轮一次声明 + 每条事件一次追加」，且事件不再需要
  为改状态而伪造；计划与记录的因果关系变成单向（内容引用步骤的地址，树不知道内容），两层各自有
  唯一写者；「打错路径多出一棵树」这个已知代价随隐式建链的退役一起消失。
- 放弃：跨轮看整体进度要宿主自己拿历轮的树（`Search` 不返回计划，这是宿主明确要的）；一步「只算
  它自己那一行、不含子步」的事件切面拿不到；同一轮内改主意只能靠再声明一次，多出来的节点由保留窗
  收，库不回收。
- 对宿主是破坏性的：计划写方法换名换形状、节点 DTO 少一个字段、状态常量少一个、事件写必须先声明
  步骤，且旧数据文件在新规则下会被显式拒绝——契约变更只经打 tag 生效。纯 MCP 宿主用不了事件绑定，
  因为计划写面按既定决策只留在 Go 侧。

  键规则本身见 `2026-09-09-turn-topic-id-is-the-only-join-key.md`。
