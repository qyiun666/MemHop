# 决策档案: 对外形态收成一种——Go module，server 面整体退役

Status: implemented

## Problem

仓库原本有两种对外形态：Go module，以及一个自带的 server 二进制——把记忆循环按多租户 HTTP 暴露，
每个租户划到一个 agent 域。后者从 v1.2.1 起存活，中途整体重写过一次，此后一直随公开面同步演进。

它带来的问题不是它错，而是它让「引擎是什么」说不清。这个 server 不持有任何引擎之外的知识：它把公开面
的方法逐个包成工具、按 URL 路径划域、管一份租户白名单、处理两种传输的启动与关闭。每一处都要跟着公开面
动一轮，而它的正确性判据只是「包得对不对」，不是「记忆这条循环准不准」。于是仓库的意图文档里专门有一
节解释哪些方法进了工具面、哪些没进、为什么某两个公开面已经删掉的读口在这一侧以便捷工具形态继续存活——
那一节的唯一读者就是那个二进制自己。

第二个代价是依赖：它是全仓唯一读 MCP 官方 SDK 的地方，这一个消费者把七个间接依赖留在依赖清单里，而
引擎自己的链路（哈希、LLM 传输、mmap）一个都用不到它们。

## Decision

仓库不再有 server 形态：不带 HTTP 面、不带工具清单、不带租户注册表，也不带后台进程。对外只剩「以 Go
module 使用公开门面」一种接入，形态描述收成一句话。

公开面本身一字未动——25 个会话方法加 7 个库方法的名单、锁范围、幂等语义与 ID 契约全部保持原样。取回
单条归档、读一轮的事件轨仍由宿主用查询条件自己组出来，不再有「不持有会话状态也能直接取」的第二条通道。

多租户没有消失，只是换了归属：按域隔离本来就是引擎语义（L3 知识图例外，它是文件级公共池）。若某个宿主
要把多个来路合成一个对外进程，那一层由它自己装配——引擎不为某一种装配方式长期持有代码。

## Alternatives considered

- **保留但冻结**（不再随公开面同步，只维持现有工具能跑）：省下的确实是每轮双份改动，代价是文档要长期
  背一句「这一侧已落后」，而冻结的面上迟早会出现已删方法的幽灵——宿主调到一个 Go 面已经取消的工具，比
  调不到更难解释。落选。
- **拆到独立仓库**（server 转为引擎的一个下游消费者）：语义最干净，也保住了已接入的宿主。但它当下没有
  第二个使用者，拆出去等于把一次删除换成一次建仓加一套 CI，跨仓版本对齐还是长期成本。落选于「没有真实
  用户」。
- **只改文档、代码标为待废弃**：废弃在这里没有出口——本仓不设弃用期，契约变更的唯一生效入口是打 tag，
  留着的代码仍然每轮要跟着公开面改。落选。
- **顺手把 `api.CodeOf` 一起删掉**（它在退役后全仓零调用）：留任的理由是「公开面即契约」——它是宿主把
  一个错误读成数值码的门面唯一口，零调用说的是本仓没有读者，不是宿主没有用处。这一条是对「零调用即删」
  纪律的一次有意例外，记在这里以免下一轮审查再把它当死代码。

## Consequences

换到的：直接依赖从四个缩到三个，server 侧那一个连同它带入的七个间接依赖一起离开依赖清单；构建 target、
CI 与本地门禁的包清单各少一项；意图文档少一整节，「对外接入方式」不再需要例外条款。

放弃的：一个开箱即用的多租户入口，以及那些不持有会话状态也能用的便捷形态。要把它做回来，起点是一个只把
门面当依赖的新二进制——门面这次没有为退役改动过任何一处，这也是「删除是安全的」那半边理由。

留下的账：`api.CodeOf` 在本仓零调用（见上）；本机 `docs/`（不入库）里的开发文档整体仍停在 v1.2.x 的结构
描述，本轮只把它涉及 server 的断言改口，其余未动。
