# 决策档案: 轮次话题 id 是 L2/L4/L6 唯一的 join key

Status: implemented

## Problem

「一轮」在三层里各有名字：L2 里它是 `Search` 铸出的话题，L4 里它是原文的归属，L6 里它是
计划树的键。这三处历史上不是同一个值——话题曾经靠一份引用清单指向原文，计划树曾经按宿主
自铸的 plan id 聚合，事件与树因此在某些轮次上对不齐。补上这一笔是因为它从来没有档案：
读代码能看到三者同键，看不出这是决定还是巧合。

## Decision

- **一轮只有一个标识**：`Search` 读场景时为「即将进行的这一轮」派生一个话题 id，它同时是
  L2 话题记录的主键、L4 内容所有记录的归属、L6 计划树的键。宿主只回传，不自造、不派生。
- **派生式（场景 + 轮次计数）而不是内容式或自造式**，所以「哪些轮次 id 合法」可由场景
  记录自己判定——这也是沉淀侧归属闸能做成纯函数的原因。
- **`Update` 因此必须同时收场景 id**：话题 id 里推不出它属于哪个场景（建话题记录需要场景），
  而归属判定需要场景的轮次计数。两参是最低成本的形状，不是历史包袱。
- 跨轮续用被明确否决：每一轮的计划树都是新的一份，不给事件加「产生它的那一轮」字段、
  不建话题到树的反向索引。

## Alternatives considered

- **计划树独立发号、按 plan id 聚合**——落选：宿主必须为「这一轮的树」再保管一个标识，
  并在每轮开始时决定复用还是新建；一旦复用就出现「一轮一树」与「N 轮一树」两种形态，
  所有按轮读取的路径都要分叉。
- **让内容按话题正文哈希归属、树按 plan id 归属**——落选：同一轮的两套键，交叉查询
  （「这一步的事件在哪」）只能靠记录里再存一份对方的 id，即引用清单的又一活形式。
- **场景 id 塞进话题 id 的可逆编码，让 `Update` 单参**——落选：id 是哈希而非编码，可逆就要
  换发号方案，代价是为了省一个参数把公开 id 的不可推测性毁掉。
- **由库在 `Update` 里猜「最新开的轮」**——落选：与「零猜测的场景归属」这条设计前提直接冲突，
  at-least-once 重试会猜错。

## Consequences

- 换来：一轮的东西按一个 id 全取；「什么可以沉淀」是一条可纯函数判定的规则；删除话题时
  三层能一起收（内容按位置键、树按归属字段）。
- 放弃：跨轮持续演化的计划树（宿主若要长任务树，得自己每轮回放计划）。
- 该键同时寻址两样东西这一事实，在门面注释、集成指南与 README 的分层表里各写一遍，
  因为它是宿主每次调用都要用到的判断，而不是一次性的实现细节。
