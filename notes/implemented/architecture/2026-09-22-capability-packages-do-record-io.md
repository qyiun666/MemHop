# 决策档案: 能力包允许携带记录读写——注入的是原语，不是仓储接口

Status: implemented

## Problem

`internal/cap` 长期被描述为「功能包·纯计算」，而 `engram` 与 `profile` 两包直接读写记录
（`core` 的 typed 读写与 `repo` 的画像读写）。这处描述与实现的落差让一次代码审查
把「能力包做 I/O」报成结构越界，并提议把全部读写收进由组合根注入的窄接口。要判断的是：
这条线到底破在哪一处——实现，还是那句描述。

## Decision

实现不变，描述改正。能力包是**身份中立、依赖经参数注入**的功能包，不是无副作用的纯函数包：

- 注入的是原语本身（`*core.StorageEngine`、`*index.L2MetaIndex`、`llmops.Chat`），
  包内不 `new` 任何依赖，也不 import `internal` 根——这条是红线，从未被踩。
- 依赖方向 `cap -> {common, repo, repo/core, repo/index}` 是正向边，本仓的架构约定允许。
- 「纯计算」这个词只在 `knowledge`/`llmops` 两包成立；`engram`（L1 建边与衰减）与
  `profile`（蒸馏样本挑选与结果写回）的工作对象本来就是盘上那批记录，读—改—写是它们
  的算法形状，不是漏进来的职责。
- `AGENTS.md` 与 `internal/agent.md` 的措辞随此改正；`internal/cap/agent.md` 早已按实话写。

## Alternatives considered

- **把那些读写收进注入的仓储接口**（原提议）：落选。它换来的不是「不踩红线」——红线
  本来没被踩——而是把 L1 巩固与画像蒸馏的读—改—写循环推到接口后面：这两段逻辑的正确性恰恰
  在于「哪一条记录在锁内被读过、又被写回什么」，藏进接口后要在两个包之间来回跳着看才能核对。
  代价是 L3 结构改动、跨多文件与两份测试，且没有任何对外变化可为它背书。
- **只收口 `profile` 那 4 处、`engram` 原样保留**：落选。同层留下两种写法，等于把
  「一个功能一个实现」在这条线上破成两个特例，下一轮审查还会再来一次。
- **反过来把 `engram`/`profile` 挪出 `cap`**：落选。它们是身份中立的算法包，挪动只改目录
  不改依赖，且 `cap` 的「一功能一包」划分仍然成立。

## Consequences

换到的是：能力包这一层的定义与实现一致，判断一个包该不该做记录读写有了可复用的判据
——**看依赖是否经注入、是否反向 import 组装层**，而不是看它有没有碰记录。
放弃的是：「能力包 = 纯函数」这个更强也更好念的性质。它只有在全部副作用都推到接口后面时才成立，
而那会让巩固与蒸馏两条路径更难就地验证。

后续接手 `cap` 的人若把「无 I/O」当成该层的既有约束，会重新提出本档案否决过的改造——
本档案的存在就是为了挡住这一次。
