# 决策档案: `Update` 蒸馏自己话题的内容，不再生产内容

Status: implemented

## Problem

`Update` 一次调用同时做三件事：写两条对话原文、铸这一轮的话题、把原文提炼成关键词。写死
「两条」在真实宿主面前不成立——一轮里可能有系统注入的上下文、可能追问一轮、可能只有一半
文本可记；而库既然自己写这两条，就必须为「重放一轮该留下什么」负责，于是需要知道这个话题
以前写过哪些归档（第二真相）。另外，公开面上另有两条轨迹读写调用与 `Update` 争同一批记录
的所有权：一个话题装了什么，有两个主人。

## Decision

- **`Update` 只剩蒸馏**：读该话题已有的对话侧记录，按槽位序渲染成带说话者标签的转录，
  一次提炼出关键词轨。入参只有场景 id 与话题 id，返回值取消（话题 id 是 `Search` 给的，
  回传一遍等于新增一桩没人消费的契约）。
- **一轮不再恒两条原文**：抽取输入是该话题下全部对话侧记录，**不含事件**——事件是执行
  过程而不是对话内容，喂进提炼会让关键词轨跟着工具调用漂移，且域锁内的 LLM 调用数会随
  事件条数线性放大。
- **无内容即拒绝**：一条对话记录都读不到（被保留窗裁光）时 `ErrInvalidQuery`，且不发起
  LLM 调用。给一个说不出话的轮次写空关键词轨，读回来像是真提炼过。
- **失败不回滚宿主的内容**：提炼失败时话题不落，先前 append 的记录原样留着。
- 一轮的热路径由 1 次调用变 3 次（两次 append + 一次 update），这是公开面收敛的代价，
  由用户明确接受。

## Alternatives considered

- **保留 `Update` 写两条原文，另开一个追加面补事件**——落选：这就是原来的形状，两种内容
  两个入口，而且「一轮恰好两条」的假设仍然焊在写路径里。
- **`Update` 接受一段任意记录数组并在内部覆写/回收**——落选：要判断哪些是本轮写的就得再记
  一份「本轮清单」，与本次删掉的第二真相同源。
- **重放时由库枚举该话题全部内容、按内容哈希配对回收**——落选：正文哈希与槽位哈希是两把
  不同的键，配对规则一旦写出来就又是一套只有 `Update` 懂的隐藏契约。
- **空内容时照常提炼（LLM 拿到空串）**——落选：多花一次调用，换来一条空关键词轨，
  而空轨与「提炼失败」在读侧无法区分。
- **让 `Update` 继续返回话题 id 以便链式调用**——落选：没有任何读者需要它，宿主手里本来就有。

## Consequences

- 换来：一轮能装宿主记下的任意多条内容；话题内容的写入者只有一个；`Update` 的语义与
  Dream 的融合入口对齐到同一个提炼函数（不再有专用的「一轮两条」渲染）。
- 放弃：`Update` 不再能阻止内容收缩。改一轮的文本时少写一条，旧那条仍活在转录里，
  收敛路径只有显式删话题或过保留窗——这条写进 append 的公开契约注释。
- 归属闸保留在沉淀这一侧：可蒸馏的话题必须是该场景真开出过的轮次，否则一次陈旧重试
  就能改写别轮的关键轨。
- 关键词提炼的输入从「两句定长文本」变成「一段渲染结果」，标签是它不塌成一坨的唯一防线，
  因此有一条去掉标签就变红的专测守着。
