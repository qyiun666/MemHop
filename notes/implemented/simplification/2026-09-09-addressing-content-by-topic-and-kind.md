# 决策档案: 归档按 (话题, 种类, 槽位) 寻址，索引由轨迹镜像改造而非新建

Status: implemented

## Problem

一条归档原先按「正文哈希」发号：写两遍同样的文本就是同一条记录，写不同文本就是不同记录。
这挡住了重放——一轮超时重试会留下两个版本的原文同时存活，要收敛就得先枚举「这个话题以前
有过哪些归档」、再给没被重写到的打墓碑，而那份枚举只能靠额外维护一份引用清单，即第二真相。

同时，事件也住在同一话题键下，但走另一套记录类型与另一个索引。融合后两种内容同层，需要一个
统一的枚举来源回答「这个话题名下有哪些槽位」。

## Decision

- **归档 id 改为可重放的派生式**：`hash("l4:" + 话题 + ":" + 槽位)`。写同一个 (话题, 槽位)
  落到同一条记录，引擎按同 id upsert 处理，因此覆写而不是叠加。派生前缀 `l4:` 与其它发号
  空间互斥，这一点由穷举断言测试钉住，而不是靠约定。
- **槽位空间是话题内跨种类共享的单一序列**，槽 1 与 2 属于对话（自动分配从 3 起），事件用
  自动分配。这个下限是正确性而非保守：宿主先记事件、后补对话时，没有下限就会让第一条事件
  被用户原文原地覆掉。
- **显式命名一个已被占用的槽位是覆写而不是报错**，跨种类也一样。这是重放语义的代价与收益
  同源处，写进公开契约注释并有专测。
- 域内索引由事件索引**就地改造**成统一的 L4 索引，条目携带种类——否则「哪些轮记了事件」会
  把只有对话的轮也报出来，场景读回会为一轮两句话读出几十条事件。

## Alternatives considered

- **扫记录桶枚举一个话题的内容**——落选：读路径每次都要过一遍全域，且「这个话题有没有内容」
  变成一次扫描而不是两次查表；索引既然已经存在（事件侧本来就有），留着它比再造一个便宜。
- **新建一份独立的 L4 镜像、与事件索引并存**——落选：两份镜像描述同一个话题名下的同一批
  记录，任何一条删除路径都要记得摘两处，漏一处的失败模式是硬错且运行期不自愈。
- **槽位仍由内容哈希、只把事件搬进 L4**——落选：保留了重放差分与那份第二真相，等于把本次
  要解决的问题原样搬新家。
- **归档 id 复合成 16 字节（话题 + 槽位）而非哈希**——落选：帧头是 26 字节定长，扩键要动帧
  布局，破坏性远大于 64 位哈希的数学碰撞上限。

## Consequences

- 换来：重放一轮不需要知道它以前写过什么；话题的内容枚举只有一个来源；索引一份。
- 放弃：「重放不再去填的槽位」不会被回收——改一轮的文本时少写一条，旧那条会继续出现在转录里，
  直到话题被删或过保留窗。库不去追踪「本轮写了哪几条」，那正是被否掉的第二真相的活形式。
- 顺序判据从「时间戳 + 角色」收敛到槽位单键：写入侧按惯例占 1/2，「问在前、答在后」由构造
  保证，不再需要一个打平用的次级键（事件的说话者字段本就是未设值）。
